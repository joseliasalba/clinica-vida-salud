# CU-01.1 — Recuperar contraseña por correo

**Estado:** Borrador de extensión de CU-01; pendiente de implementación y aceptación. Su obligatoriedad como requisito académico está por verificar.

| Campo | Especificación |
| --- | --- |
| Objetivo | Permitir que el titular de un correo registrado establezca una nueva contraseña |
| Actor principal | Usuario que perdió su contraseña |
| Actor secundario | Servicio de correo |
| Requisitos relacionados | Propuesta del usuario; vinculado a RF01, pendiente de confirmar alcance original |
| Precondiciones | Cuenta activa con correo registrado; transporte de correo configurado |
| Evento que inicia el caso | Selecciona «Olvidé mi contraseña» |
| Resultado de éxito | Contraseña actualizada; enlace consumido; sesiones anteriores revocadas; acceso mediante login normal |
| Garantías ante un fallo | No revelar si existe una cuenta; no cambiar la contraseña ni reactivar una cuenta inactiva |

## Flujo principal

| Paso | Acción del actor | Respuesta del sistema |
| --- | --- | --- |
| 1 | Solicita recuperar acceso con su correo | Valida formato, CSRF y límites; muestra siempre una confirmación genérica |
| 2 | — | Para una cuenta activa, genera un enlace seguro con token almacenado como hash y vencimiento de quince minutos |
| 3 | Abre el enlace recibido | Valida el enlace sin consumirlo por el simple GET y muestra nueva contraseña y confirmación |
| 4 | Envía la nueva clave | Revalida cuenta activa, token, expiración y política en servidor |
| 5 | — | Actualiza el hash y consume el token de forma atómica, rota el token de recordar sesión e invalida las sesiones anteriores |
| 6 | Regresa al login | Muestra confirmación e informa por correo del cambio; no inicia sesión automáticamente |

## Excepciones

| Código | Origen | Situación | Resultado |
| --- | --- | --- | --- |
| A1 | Solicitud | Correo inexistente o cuenta inactiva | Misma confirmación; sin envío ni reactivación |
| A2 | Solicitud | Exceso de solicitudes | Limitación uniforme por IP y correo; no bloquear la cuenta por pedir un enlace |
| A3 | Enlace | Token vencido, alterado o consumido | Rechazo genérico y opción de solicitar otro |
| A4 | Nueva clave | Confirmación distinta o política incumplida | Error de validación; el token sigue vigente hasta su uso o expiración |
| A5 | Correo | Falla el envío | Registro técnico sin secretos y respuesta pública equivalente; permitir reintento limitado y comprobar el fallo operativamente |
| A6 | Cambio | Dos envíos simultáneos del mismo token | Solo uno puede completar el cambio |
| A7 | Cambio | Cuenta desactivada después de solicitar el enlace | Se rechaza sin reactivar la cuenta |

## Diseño y reglas propuestas

- Usar Password Broker y notificaciones/mail de Laravel, con `password_reset_tokens` existente. Adaptar el ingreso `correo` y el callback de actualización a `contrasena_hash`; el nombre técnico `email` de la tabla de tokens no obliga a renombrar `usuarios.correo`.
- No añadir PHPMailer ni `recuperacion_passwords`: duplicarían funciones disponibles. No exigir SHA-256 específicamente; usar el almacenamiento de tokens del framework y verificar su comportamiento.
- Ajustar expiración de sesenta a quince minutos. Propuesta de reenvío: un minuto por correo, más un límite global por IP. Un nuevo enlace invalida el anterior.
- Generar URLs mediante rutas y un dominio de aplicación confiable, nunca concatenando el Host enviado por el navegador. HTTPS en despliegue; HTTP solo local.
- Respuestas equivalentes en contenido y comportamiento temporal para cuentas existentes e inexistentes. Evitar que SMTP síncrono revele la existencia del correo; usar cola con worker verificado o un mecanismo equivalente comprobado.
- No registrar tokens ni enlaces completos en logs de uso real. En desarrollo, el transporte log solo demuestra generación; no acredita entrega SMTP.
- Propuesta de claves sin MFA: mínimo quince caracteres, admitir frases, espacios y Unicode, sin regex obligatoria de mayúsculas/números/símbolos; rechazar claves comunes y confirmar la clave. Definir un máximo de al menos 64 caracteres y verificar algoritmo y límites de bytes antes de implementarlo; nunca truncar silenciosamente. Si la docente exige composición, registrarlo como restricción académica.
- Aplicar la misma política en registro, creación de cuentas y restablecimiento. JavaScript solo ofrece ayuda visual; la validación del servidor es obligatoria.
- Revocar sesiones antiguas requiere una solución explícita: middleware `auth.session` con comprobación de cambio de hash o almacenamiento de sesiones en base de datos. La sesión en archivos actual no permite asumir que actualizar la clave basta. Probar dos clientes independientes.
- Consumir el token y actualizar la contraseña dentro de una operación transaccional con control de concurrencia; no dar por garantizado el uso único simultáneo por utilizar el broker.
- No habilitar «recordarme» en la primera versión, pero rotar el token existente por seguridad.

## Rutas previstas

GET/POST `/recuperar-contrasena`, GET `/restablecer-contrasena/{token}` y POST `/restablecer-contrasena`. Formularios POST con CSRF y limitación de intentos. Las vistas se ubican en `sistema/frontend/views/auth/`.

## Criterios de aceptación

- Respuesta pública equivalente para correo existente, inexistente e inactivo, sin envío al destinatario desconocido o inactivo.
- Límites efectivos de solicitud y reenvío; token almacenado como hash, vencido a los quince minutos y válido una sola vez.
- Nuevo enlace invalida el anterior; abrir un enlace sin enviar la nueva clave no lo consume.
- Un restablecimiento exitoso impide usar la clave anterior y exige login normal.
- Las sesiones previas dejan de acceder, incluido un segundo navegador; ninguna cuenta inactiva se reactiva.
- Dos solicitudes simultáneas con el mismo token producen como máximo un cambio exitoso.
- Sin JavaScript, se siguen validando clave y confirmación.
- El fallo de SMTP no expone información de la cuenta ni se presenta como una entrega comprobada.

## Evidencia de pruebas

Pendiente. Usar notificaciones simuladas para pruebas automatizadas y una prueba separada del transporte real de correo. No se necesita enviar correos externos durante las pruebas de la lógica.
